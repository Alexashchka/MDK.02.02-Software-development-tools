Практическая работа №1

Тема работы

Название: Разработка модульной структуры проекта

Объект проектирования: программное обеспечение курсового проекта студента.

Цели и задачи

Цель: приобрести навыки проектирования модульной архитектуры программного обеспечения, декомпозиции монолитного приложения на независимые модули/сервисы и формализации межмодульных связей.

Задачи:

  • выполнить анализ предметной области своего курсового проекта и выделить независимые функциональные модули;
  • разработать спецификацию декомпозиции модулей и зон их ответственности;
  • спроектировать распределение данных и изолированных хранилищ между модулями;
  • описать спецификацию межмодульных контрактов обмена данными (API / DTO).

Теоретические материалы

Базовыми строительными блоками качественной программной системы являются независимые модули. При монолитной архитектуре все модули и сервисы размещаются в рамках одного решения и единого исполняемого процесса, обращаясь к общей базе данных. Это приводит к сильной связанности, когда изменения в одном модуле могут непреднамеренно сломать другой.

При проектировании модульной и микросервисной структуры ключевыми критериями являются:
  • Высокая связность: каждый модуль решает только одну обособленную подзадачу предметной области;
  • Слабая зацепленность: модули взаимодействуют друг с другом исключительно через четко заданные интерфейсы и контракты данных;
  • Изоляция данных: модуль самостоятельно управляет своим хранилищем данных. Прямые связи внешних ключей (FK) и межмодульные запросы JOIN к таблицам других модулей исключаются;
  • Шлюз (API Gateway): выступает единой точкой входа для клиентской программы на C#, маршрутизируя запросы к соответствующим модулям/сервисам.

Задания для выполнения

На основе своего курсового проекта разработать проект модульной декомпозиции, включающий 2 схемы и 3 аналитические таблицы:

1. Графические схемы

  1. Схема «AS-IS» (Текущая монолитная структура): изобразить архитектуру проекта в текущем виде (клиентское приложение на C#, единый монолитный бэкенд на ASP.NET с набором контроллеров и общая база данных).
  2. Схема «TO-BE» (Перспективная модульно-сервисная структура): изобразить систему после декомпозиции (C# клиент, шлюз API Gateway, не менее 2–3 независимых сервисных модулей и изолированные базы/хранилища каждого модуля).

Схемы выполняются в любом удобном графическом редакторе (draw.io, Visio, StarUML и др.).
